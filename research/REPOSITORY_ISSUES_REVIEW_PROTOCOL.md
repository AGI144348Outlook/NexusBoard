It may compare cross-project issues, unresolved interface requirements, standards, semantic and human-computer-interface questions, and proposed Mashet Glyph–MCP bindings.

## Per-review workflow
1. Enumerate accessible repositories; record unavailable or restricted repositories without inventing coverage.
2. Resume a durable checkpoint; prioritize new substantive updates, integration blockers, decisions, security permissions, MCP/skills, capabilities, UI workflows and evidence.
3. Read issues and relevant comments; preserve source repo, issue number, URL, visibility, timestamps, review date, status and source revision marker. Do not equate list discovery with reading.
4. Classify observations, claims, hypotheses, decisions, proposed changes, test results, unverified assertions, contradictions, ownership and authorizations.
5. Compare across repositories with explicit source links; avoid forced identity or incompatible-state merging.
6. Produce a bounded privacy-safe, researcher-readable NexusBoard report where substantive. Link proposed Mashet Glyph–MCP expressions to requirements; these are proposals until verified.
7. Create/update records in the authenticated Neon Documentation Catalog only when deployed, credentials and permissions allow, with visibility metadata and a content-minimization policy.
8. Track publication candidates separately for the textbook editorial branch and obtain permissions before commercialization.
9. Report actual issue/repository coverage and next checkpoint; never declare a whole-account review completed from a bounded sample.

## Privacy / public boundary
Private issue content may be summarized for authorized private use but MUST NOT be pasted into NexusBoard's public main branch or public textbook branch. Public-facing reports use generalized architectural findings, not verbatim private issue details. Store restricted crosswalks in an access-controlled private catalog, with source pointers and audit trails. Search/discovery grants no publication or write authority.

## Repository testing restriction
Before tests, benchmarks, exploratory repository diagnostics, regression or CI: publish a prospective Issue/Discussion entry in the affected repo describing Timothy's discussion, problem, hypothesis, method, expected result and falsifier. After testing update same thread with procedure, observations vs interpretations, failures, evidence, limitations and next actions. If posting fails, stop before tests.

## Catalog record shape
Repository card → Issue card → Evidence/source cards → Analysis report → optional glyph/MCP mapping → optional textbook candidate → Review checkpoint and governance decision. Every edge carries source and validity status. Catalog data is not authorization to execute tools.
